# ai-agent-learning
> 个人AI学习实战仓库 | 个人学习记录。从 Python 基础补起，逐步手写实现 AI Agent 与 RAG 的核心链路。
> 
> 说明：仓库中的早期代码有一部分是在 AI 辅助下完成的，我正在逐个重写成能独立讲解、可面试复盘的版本。本文档仅展示目前已完全吃透、能讲清原理的内容。

## 📁 项目模块
- `simple_agent_demo.py`：简易对话客户端，实现对话记忆持久化（JSON）、历史截断、异常处理（早期练习作品，AI辅助比例较高，尚未重写；暂不纳入「项目深度复盘」范畴，不作为面试展示项目）
- `notes_loader.py`：语料加载层 —— 递归扫描笔记库里的 `.md`，保留「路径 + 正文」两份信息；**语料根目录三级解析**（`NOTES_ROOT` 环境变量 → `~/ai-agent-notes` → 仓库自带 `sample_notes/`），所以别人 clone 下来不配任何路径也能跑；环境级错误 fail fast（语料目录不存在直接退出），单文件级错误跳过并回报（不静默丢数据）；BOM 计数可见（实测本机语料 0 篇带 BOM）。**两道闸门叠加**：**白名单 `INCLUDE_TOPS`** 管范围（只有 `01-初始知识点` / `02-RAG项目` / `03-Agent项目` 三章进语料，散在根目录下的散篇同样不入），**黑名单 `EXCLUDE_DIRS`** 管细节（在范围内再剔 `.obsidian` / `_附件` / `99-原始存档` / `复习材料` / `04-变更卡` / `03-变更卡`）。**目录过滤按「路径分段」判（不做子串匹配，避免误杀同名前缀目录）**；并带**三条哨兵**：① 白名单里每一项能否在整棵目录树里找到同名目录（写错 = **整章静默消失**，篇数只是"看起来正常变少"）② 黑名单里每一项能否在**整棵目录树**里找到同名目录（原来只查第一层 —— 重构后 `04-变更卡` 挪到第二层，旧写法会误报「名字写错」；**假红也是 bug**）③ 白名单**外面**还有哪些顶层目录 —— 每次都摆出来，因为白名单失效的方向是「静默变少」，不打印就查不出来
- `basic_rag_pipeline.py`：内存版完整 RAG 链路，纯手写分块、向量化、检索、Prompt 组装；语料改为从 `notes_loader` **读全库真实笔记正文**（不再写死示例文本，也不再只取一篇）。**五维验收指标 5/5 落地**；管线分两段：`build_corpus()` 做「文档级」处理（逐篇分块 → 补 `header`/`source` → 逐篇跑四道校验），再把全库块一次性向量化建库、检索（「全局级」）。已修 `overlap=0` 死角（见文末「变更卡 01」）
  - 💡 关键设计决策（原创优化）：`basic_rag_pipeline` 递归切分 overlap 防重复叠加设计
    - 传统递归分块存在缺陷：每一层递归都做 overlap 更叠上下文，递归越深，重叠内容叠加越多，最终文本大量冗余、失真。
    - 我增设 **_raw 标记参数**，做层级控制：
      - ✅ 只在最外层做一次 overlap 拼接 + 参数校验
      - ✅ 内层递归只负责切分文本，不再重复叠加重叠区域，大幅减少冗余文本，同时避免重复参数校验，提升分块精度与执行效率。
- `tool_agent.py`：无框架手写 ReAct Agent（DeepSeek API + Function Calling），完整实现工具调用循环、分层重试、边界容错
- `tool_agent_langgraph.py`：LangGraph `StateGraph` 版 ReAct Agent，复用 `tool_agent.py` 的工具定义/映射/重试，改用状态图（`add_messages` 自动归并消息 + 条件边路由）实现推理循环；挂 `SqliteSaver` checkpointer 把状态落盘、支持跨轮对话记忆；并对「同一工具连续重复调用」做熔断（`repeat_count`）
- `eval_rag.py`：**评测线** —— 四层结构（数据 / 检索 / 指标 / 报告），`Chroma` 检索 → 双层指标 → 存档 → 与上次对比。判定从「文件级」升级为**块级**：文件对 **且** 正文含 gold 的 `must_contain` 逐字片段才算命中，专门排除「召回对了文件、但召回的块只是 frontmatter / 标题行」的假绿。四项指标 `doc_recall@5` / `chunk_hit@5` / `MRR` / `avg_rank_hit`；每次运行存 `eval_runs/*.json` 并自动对比，输出「有效 / 正向 / 无影响 / 负向」。设计与踩坑见 [评测线-设计与踩坑.md](评测线-设计与踩坑.md)
- `chroma_store.py`：**向量持久化层** —— `build_index()` 建库 / `search()` 检索 / `search_as_chunks()` 适配器。显式指定 `hnsw:space="cosine"`（`距离 = 1 - 余弦相似度`）；`search_as_chunks()` 把 Chroma 返回的 `(距离, 文本, 元数据)` 重新包装回 `ChunkItem`，做到**对外接口不变、只换实现**，因此 `/ask` 只改了一行。建库策略：整个目录 `rmtree` 重建 + 一次性 `add`（分批写会生成多个 segment，跨进程加载时只要有一个段读不出就整体失败）
- `chroma_build.py`：建库脚本，跑一次即可（当前 50 篇 → **2818** 个块 → 512 维写入磁盘；纯空白块已在入库前滤掉，见「变更卡 14」）
- `chroma_compare.py`：**新旧检索对账** —— 拿内存版余弦实现当标准答案，比对 Chroma top-5 的「文件名 + 起始位置」，实测**完全一致**。这是「换库没改坏」的第一条证据；第二条是同口径下 `Recall@5` 换库前后均为 90%
- `chroma_demo.py`：Chroma 最小可运行例子（3 条文本 + 建库 + 查询），用于先跑通再接项目
- `practice/`：日常练习归档目录，按「专题_序号_名称」命名，不再散落在 PyCharm 工程里（当前 LangGraph 四练：`01` TypedDict 基础 → `02` 状态手动流转 → `03` StateGraph + add_messages → `03_Annotated` 在 03 基础上加 SqliteSaver，验证状态持久化）。四练的定位与对照实验详见 [`practice/README.md`](practice/README.md)

- `FAST_API.py`：**RAG 服务化入口** —— 把 `basic_rag_pipeline.py` 的六环包成 `POST /ask`，一次请求完成「检索 → 组装 → 生成 → 带出处返回」。**全局装载区与请求区严格分开**：语料加载只在启动时跑一次，检索 / 裁剪 / 组装 / 生成每次请求跑一次。**检索已改为从磁盘上的 Chroma 向量库读**（2026-10-25），不再每次启动重算 3918 个块的向量 —— 实测启动耗时由约 **120 秒降至 10 秒**（其中 90 秒来自「不再重算向量」，20 秒来自 tiktoken/磁盘缓存，剩余 10 秒是 `import torch` + 加载模型的固定成本）。返回体含 `answer` 与 `sources`（文件名 + 行号 + 标题），`sources` 在**裁剪上下文之前**采集，避免块被截断后丢失出处。**运维三件套（2026-10-26）**：`GET /health` 健康检查（把语料块数与库内条数并排吐出来，`status` 为 `ok`/`degraded`，不一致时直接给修法）、`GET /` 接口清单（不返回裸 404）、`/ask` 请求分段计时日志 —— 目标只有一个：**服务出问题时，接手的人不读代码也能查**。
- `RAG_main.py`：**一条命令入口** —— `python RAG_main.py "你的问题"` 完成「检索 → token 预算裁剪 → 生成 → 打印出处」。**自带冷启动**：库不存在/为空/collection 缺失时自动走 `load_docs → build_corpus → encode → build_index`，建完对账（块数 == 库内条数）后再回答；换台机器 clone 下来不用先手动建库。出处格式为「文件名 + 字符区间 + 小节标题」。

### 📦 项目依赖
见根目录 **`requirements.txt`**（唯一真源，不要在别处再抄一份版本清单 —— 两份清单必然漂移）。
核心：`sentence-transformers`（向量化）、`numpy`（余弦相似度）、`tiktoken`（上下文裁剪）、`fastapi` + `uvicorn`（服务化）、`langgraph` + `langchain-openai`（状态图版 Agent）。

## 🚀 Quick Start

### 1. 获取代码
```bash
git clone https://github.com/luotianwen123/ai-agent-learning.git
cd ai-agent-learning
```

### 2. 环境准备
建议 Python 3.9+（本仓库已用 **3.12** 实测）。依赖见根目录 `requirements.txt`：

```bash
python -m venv .venv
# Windows
.venv\Scripts\activate
# macOS / Linux
source .venv/bin/activate

pip install -r requirements.txt
```

> 首次装 `sentence-transformers` 会连带拉入 `torch`，体积较大（数百 MB）。国内网络慢时先配 `pip` 镜像。

### 3. 配置 API Key
四个模块均调用 DeepSeek API（模型 `deepseek-chat`）。在项目根目录新建 `.env` 文件：

```dotenv
OPENAI_API_KEY=你的_DeepSeek_API_Key
# 可选：国内直连 HuggingFace 缓慢时走镜像（basic_rag_pipeline.py 首次运行要下模型）
HF_ENDPOINT=https://hf-mirror.com
# 模型已缓存到本地后建议开启：跳过启动时的联网版本检查
# 不开的话，镜像响应慢会表现为「程序停在分块日志后不动、CPU 0%、不报错」——见「变更卡 06」
HF_HUB_OFFLINE=1
```

> ⚠️ `HF_HUB_OFFLINE` 必须在**所有第三方 import 之前**生效。本项目靠 `load_dotenv()` 写在 `FAST_API.py` 第一行的顺序保证；写到别处会失效（库已经把配置读走了）。
> 部署到**没有本地模型缓存**的服务器时，这个变量要反过来去掉，否则会直接报找不到模型。

> 仓库自带 **`.env.example`** 模板：复制为项目**根目录**下的 `.env` 再填 Key（`copy .env.example .env`）。
> ⚠️ `.env` 必须放在**本项目根目录**，不要放在上级目录 —— 否则别人 clone 下来会因取不到 `OPENAI_API_KEY` 报 401。
> `.env`、`config.json`、`history.json` 均已在 `.gitignore` 中，不会被提交。

### 3.5 语料从哪来（**不配也能跑**）

程序按三级顺序找语料目录，命中即止：

| 顺序 | 位置 | 什么时候命中 |
|---|---|---|
| ① | `.env` 里的 `NOTES_ROOT` | 你显式指定了 |
| ② | `~/ai-agent-notes` | 你有自己的笔记库（作者的默认位置） |
| ③ | 仓库自带 `sample_notes/` | **以上都没有** —— 别人 clone 下来的默认情况 |

⇒ **clone 下来不配 `NOTES_ROOT` 也能直接跑**，用的是 `sample_notes/` 里 4 篇演示笔记（RAG 概念 / 分块与重叠 / 评测指标 / ReAct 循环）。

想换成自己的笔记库，在 `.env` 里加一行：

```dotenv
NOTES_ROOT=D:/我的笔记库
```

启动时第一行就会打印当前用的是哪个目录，不用猜：

```
【语料根目录】...\sample_notes
【语料过滤】扫描 4 篇 → 入选 4 篇｜排除 0 篇（无）
```

> ⚠️ **语料目录结构要匹配白名单**：`notes_loader.py` 只收 `01-初始知识点` / `02-RAG项目` / `03-Agent项目` 这三个顶层目录下的 `.md`。你的笔记库如果顶层目录名不同，会**一篇都不收且不报错**（白名单失效方向是"静默变少"）。
> 为此程序每次都会把白名单外的顶层目录列出来：`ℹ️ 白名单外·整目录不入语料：...` —— 看到这句就说明有内容被挡在门外。

> 📌 `eval_rag.py` 的 10 道 gold 题是针对作者自己笔记库标注的回归集。用 `sample_notes/` 跑评测，指标没有意义（考卷对不上语料），但**程序本身能跑通**。


### 4. 运行各模块

> **只想最快看到效果**：跳到 [⑦ `RAG_main.py`](#-rag_mainpy--一条命令问一个问题自带冷启动模型)

**⓪ `notes_loader.py` —— 语料加载（跑 RAG 前先看这个）**

```bash
python notes_loader.py
```

输出：篇数 / 总字符数 / 最长的一篇 / 带 BOM 的篇数 / 被跳过的文件（含原因）。
语料目录不存在属环境级错误，直接 `SystemExit` 退出；某一篇读不出来属单文件级错误，**跳过并报告**，不静默丢数据。

**① `tool_agent.py` —— 手写 ReAct Agent（推荐先跑这个）**

```bash
# 直接提问
python tool_agent.py "现在几点了？帮我算一下 (128 + 370) * 3"

# 自定义最大推理轮次（默认 5）
python tool_agent.py "北京现在天气怎么样？" --max-steps 8

# 不传问题则打印帮助
python tool_agent.py
```

内置 4 类工具：时间查询、计算器、本地文件读取、真实天气 API 请求。
运行后会依次打印模型的思考、每次工具调用与回填结果，最后输出 `===== 最终答案 =====`。

**② `basic_rag_pipeline.py` —— 手写完整 RAG 链路**

```bash
python basic_rag_pipeline.py
```

⚠️ 四点注意：
- 首次运行会自动下载 embedding 模型 `BAAI/bge-small-zh-v1.5`（约 100MB），需要联网等待。国内网络慢时，在 `.env` 里配 `HF_ENDPOINT=https://hf-mirror.com` 走镜像。
- **`.env` 必须在所有第三方库 import 之前加载**：`huggingface_hub` 在模块导入时就会读取 `HF_ENDPOINT` 并存入常量，之后才调 `load_dotenv()` 已经太晚，镜像不会生效。调整 import 顺序时别把这个先后关系弄反。
- 语料来自 `notes_loader` 扫描的笔记库**全库正文**（不再写死 demo 文本）；`__main__` 里只写死 `query`（检索问题）和 `max_chunk_size / overlap` 两个参数，换问题改 `query` 即可。
- 脚本会打印组装完成的完整 Prompt，并调用大模型输出最终回答。

**②.5 `chroma_build.py` —— 建向量库（跑服务前先跑一次，之后不用再跑）**

```bash
python chroma_build.py      # 建库 + 建完自检
python chroma_compare.py    # 可选：和内存版对账，验证换库没改坏
```

⚠️ 三点注意（都是踩过的坑）：
- **库目录必须放在纯英文路径**（默认 `~/chroma_notes_db`，可用环境变量 `CHROMA_DB_PATH` 覆盖）。Chroma 1.x 是 Rust 后端，**路径含中文会导致索引读不出来**，报错是 `Error loading hnsw index`；现象很迷惑 —— 同一个进程刚写完能查、换个进程就读不出来。
- **库不进版本库**（已在 `.gitignore`）。笔记库内容变了要重新跑一次 `chroma_build.py`，否则服务查到的还是旧语料。
- 判据不是「库里有多少条」，而是**换一个新进程去查，能不能查出东西**。`collection.count()` 读的是元数据表，索引没落盘它照样返回正确条数 —— 这是典型的假绿。

**③ `simple_agent_demo.py` —— 带持久化记忆的对话客户端**

该模块从 `config.json` 读取配置（文件被 gitignore，需手动创建）：

```json
{
  "agent_name": "学习助手",
  "system_prompt": "你是一个耐心的 AI 学习助手。",
  "api_key": "你的_DeepSeek_API_Key",
  "api_url": "https://api.deepseek.com/chat/completions",
  "max_history_len": 10
}
```

然后运行：

```bash
python simple_agent_demo.py
```

- `max_history_len` 可选，默认 10，超出后自动截断最早的历史。
- 对话中每轮都会把历史写入 `history.json`，下次启动可延续上下文。
- 输入 `exit` 退出。

**④ `tool_agent_langgraph.py` —— LangGraph 版 ReAct Agent**

```bash
python tool_agent_langgraph.py
```

复用 `tool_agent.py` 的全部工具定义、工具映射、重试装饰器与最大步数配置，改用 LangGraph `StateGraph` 搭建推理循环：`messages` 用 `Annotated[list, add_messages]` 让框架自动追加、`route_agent` 条件边判断「继续调工具 / 终止」，再挂 `SqliteSaver` checkpointer（状态落在脚本同目录的 `checkpoints.sqlite`，路径用 `os.path.dirname(os.path.abspath(__file__))` 锚定、不受启动目录影响）、靠同一个 `thread_id` 让多次 `invoke` 共享记忆。另对「同一工具连续重复调用」做熔断：连续超过 `MAX_REPEAT`（默认 3）次即走 `finish_repeat_limit` 收尾，第 4 次请求不再执行。需额外安装 `langchain-openai`、`langgraph`。

**⑤ `eval_rag.py` —— 评测线（块级 Recall@K + MRR）**

```bash
python eval_rag.py
```

输出顺序：一张表（每题 `rank` / `doc@5` / `hit@5`）→ 四项指标 → 存档文件名 → 与上一次运行的对比结论。

- **判定是块级的**：文件名对 **且** 正文含该题 `must_contain` 的逐字片段，才算命中。
  只判文件名会把「frontmatter / 标题行」也算中 → 假绿。
- **K 可调**：脚本顶部 `K_RETRIEVE=10`（先捞几条，用于算 rank）、`K_REPORT=5`（对外报 @5）。
- **会自动对比**：每次运行存 `eval_runs/*.json`，与上一次比指标升降 + 哪些题变好/变坏，
  并给结论（有效 / 正向 / 无影响 / 负向）。
- ⚠️ **已知局限**：当前 10 题是「宽版 gold」（参考检索结果标注，存在测试泄漏），
  只能当**回归集**用；要衡量「进步」需另加闭卷难例题。详见
  [评测线-设计与踩坑.md](评测线-设计与踩坑.md) 第七节。

**⑥ `FAST_API.py` —— RAG 服务化入口（`POST /ask` + 运维三件套）**

```bash
python FAST_API.py
```

启动成功的判据**不是「日志刷完了」**，而是这三条同时成立：

```bash
# ① 进程不退，并打印 Uvicorn running on http://127.0.0.1:8000
# ② 接口清单（不裸 404）
curl http://127.0.0.1:8000/
# ③ 健康检查：库和语料对不对得上
curl http://127.0.0.1:8000/health
```

`/health` 的关键设计：**只返回 200 是不够的** —— 库过期时服务照样 200、照样答，只是答的是旧数据。
所以它把 `corpus.chunks`（当前语料分块数）与 `index.chunks`（库内条数）并排吐出来：

```json
{
  "status": "ok",
  "corpus": {"docs": 50, "chunks": 2818, "chunk_failures": 0},
```

### 项目一：`tool_agent.py` | 无框架手写 ReAct Agent
1. **实现内容**
基于 DeepSeek API + Function Calling，零框架手写 ReAct 智能体。核心采用 while 循环实现模型思考、工具调用、结果回填的完整闭环。通过「工具名 - 函数对象」映射表，实现动态查表调用工具，直至模型主动结束任务。代码规模约 190 行，内置 4 类可用工具：时间查询、计算器、本地文件读取、真实天气 API 请求，支持命令行直接调用与帮助文档提示。

2. **核心问题与解决思路**
   - **问题1：异常不分层，永久性错误无故重试3次，造成资源浪费与卡顿**
     原始装饰器对所有异常统一重试，导致参数错误、文件不存在等永远不会恢复的错误依旧重试，造成资源浪费与卡顿。
     解决：做异常分层。区分「永久性错误（语法、参数、文件不存在）直接终止返回」和「临时错误（网络波动）延迟重试」，精准控制重试逻辑。
   - **问题2：参数化配置暴露隐藏边界 Bug**
     早期最大步数写死，模型一般2轮即可完成任务，边界问题从未暴露。新增 `--max-steps` 可配置参数后，出现「模型正常完成任务仍提示超限」的误判。
     解决：使用 `while...else` 语法区分循环退出场景，精准区分「模型主动结束」和「步数超限被动结束」，修复边界误判。
     工程感悟：可配置化会把原本不可能触发的边界问题，变成用户可随时触发的显性问题，倒逼代码健壮性提升。
   - **问题3：不规范提交导致公共仓库代码损坏**
     代码缩进错误未编译校验直接提交，导致仓库文件存在语法错误，持续3天未发现。
     解决：建立工程习惯，修改代码后强制执行 `py_compile` 编译校验，杜绝坏代码入版本库。

3. **项目总结与后续方向**
目前四大工具全部跑通，真实网络 API 验证重试机制有效性，装饰器调用链、闭包、wraps 原理全部吃透。
后续优化：替换 eval 实现、统一全局常量、精细化日志输出。

### 项目二：`basic_rag_pipeline.py` | 手写完整 RAG 链路
1. **实现内容**
不依赖任何 RAG 框架，纯手写内存版完整 RAG 链路：文本递归切分、重叠拼接、向量化、相似度检索、上下文组装，全程自主实现。语料来源改为 `notes_loader.py` 读**全库**真实笔记正文（不再写死示例文本，也不再只取一篇）；管线分两段：`build_corpus()` 逐篇分块、补 `header`/`source`、**逐篇**跑四道校验（文档级），再把全库块一次性向量化建库并检索（全局级）。分块结果不再是裸字符串，而是带位置与出身的 `ChunkPosition`（见文末「变更卡 03」）。

**真语料实测**（`max_chunk_size=150 / overlap=30`）：

- **单篇**（`06-计划与复盘/学习计划总表.md`，12,661 字，10-07 口径）：**139 块 · 边界不合格 0/138 · 还原 12661/12661（四道校验全绿）**
- **全库**（50 篇，10-09 口径）：**逐篇四道校验 0 失败 · 全库 2567 块 · 重叠一致性校验真正比较 2517 对**

⚠️ **语料是活的**：篇数与块数随笔记增长而变（当前入选 51 篇），上面只是「截至某一刻」的实测值。

2. **核心难点：4 个静默 Bug + 换真语料后暴露的 3 个问题**
所有 Bug 均为程序不报错、输出看似正常、底层逻辑失效的静默故障，极难排查。
- **递归切分静默降级**：`rfind` 匹配逻辑导致递归失效，实际降级为定长切分。当时并没有现成的检查工具，是靠人工按「每个块的结尾是否落在合法分隔符上」这个判据逐块核对才定位到的；这个人工判据后来才被固化成代码（即下方第 5 项指标）
- **尾部数据丢失**：提前返回逻辑绕过重叠合并，导致尾部文本截断丢失
- **生成空文本块**：缓冲区未做空判断直接刷新，产生无效空块
- **重叠上下文失效**：反向截断砍掉前置重叠内容，导致上下文拼接失效

以下三条是 2026-10-06 把 230 字示例换成 12,661 字真实笔记之后暴露的（**前 4 个 bug 在一个太"顺"的小样本上全绿**）：

- **块尾不再落在分隔符上 —— 硬切断在半句话中间**：第 5 项指标报警 **70 / 113**。根因是 Markdown 表格行单行长达 167–199 字，超过搜索窗口（`max_chunk_size - overlap = 120`），三层分隔符在窗口内一个都找不到 → 走硬切兜底。**修法靠数据不靠直觉**：先试加 `|`，不合格数只从 **70 → 69**；统计每种候选分隔符在失败块里的分布后发现 `|` 只在 30/40 个失败块出现且位置偏前，而**空格在 40/40 个失败块里都出现、且最后出现位置都在窗口后段** → 加上空格后不合格数 **69 → 0**，块数 114 → 139（+22%）。最终 `SEPARATORS = ["\n\n", "。", "\n", "|", "，", "、", "；", "：", " "]`
- **报错只说「第 39 块不合格」，人无法定位**：给分块补位置信息 `ChunkPosition`（`text` / `start` / `end` / **`actual_overlap`** / `truncated` / `source` / `index`），并用 `row_num()`（行号）+ `subsection_location()`（所在小节）把下标翻译成人能直接跳过去的位置 —— 报错从「第 39 块」升级为「**第 146–148 行 ·《八、债清单》· 块尾 `…pipeline.py` 可能跑不起来；`**」。关键设计：`actual_overlap` **必须当场记录**，它是"上一块比 overlap 短时 `prev[-overlap:]` 取不满"的结果，事后反推要重新实现一遍拼接规则。
- **写死的 overlap 与实际重叠不一致 —— 静默丢 5 个字**：第 3 项指标报 `还原 12656 / 原文 12661`，**程序一个异常都不抛**。根因：`overlap` 是变量，但「每块开头恰好有 overlap 个字」是**假设**；有一块上一块只有 25 字 → 实际只重叠 25 字，而还原式写死剁 30 → **多剁 5 个字**。改成按「每块实际重叠」对账后：`丢字数 = overlap(30) − actual_overlap(25) = 5` 当场对平 —— 第 3 项还原 **12661 / 12661**、第 1 项 **0 对不匹配**，而第 5 项的数字**一动没动**（证明这次改动没有副作用）。

3. **自研五维验收指标（核心亮点）**
解决「能跑但跑不对」的行业痛点，建立量化验收标准。**进度如实标注：五项已全部落地为代码**（第 4 项于 2026-09-28 补齐：把参数写进 `assert` 的报错文案）。

| # | 指标 | 状态 |
| --- | --- | --- |
| 1 | 重叠长度一致性校验 | ✅ **已实现**（`overlap=0` 场景未覆盖，见下） |
| 2 | 分块长度合规校验 | ✅ **已实现** |
| 3 | 原文内容零丢失校验 | ✅ **已实现**（`overlap=0` 场景未覆盖，见下） |
| 4 | 测试参数可追溯记录 | ✅ **已实现**（参数写进 `assert` 的报错文案 —— "会喊疼的那一行"） |
| 5 | 分块边界必须落在合法分隔符上（唯一可检测递归降级的指标） | ✅ **已实现** |

第 5 项的落地形态是 `check_boundary(chunks, separators)`，返回「不合格块数 / 已检查块数 / 不合格下标」三元组，`__main__` 里用两道断言卡住：

- **哨兵断言** `checked_num > 0`：防止只分出 1 块时断言空跑。此处术语要分清——`checked_num=0` 时「不合格数 0」只是因为根本没检查过任何边界，属**假阴性（漏报，该报没报）**，而非假阳性（误报）；表现出来就是空跑导致的「假通过」
- **三元组整体断言** `boundary_result == (0, checked_num, [])`：所有非末尾块都必须以合法分隔符结尾
- 校验与分块共用同一份全局 `SEPARATORS`，避免两处分隔符定义漂移

**该指标已通过「故意注入 bug」的反向验证**——人为破坏分块逻辑后，断言确实报错拦下，证明它不是「永远通过」的摆设。它也是五项里唯一能检测递归切分静默降级的指标。

第 1 项的落地形态是 `check_overlap_consistency(chunks, overlap)`：逐对比较第 i 块末尾 `overlap` 个字符与第 i+1 块开头 `overlap` 个字符，返回「是否全部合法 / 错误对数 / 坏对下标」三元组（下标 i 表示 `chunks[i]` 与 `chunks[i+1]` 这一对校验失败），另配 `len(chunks) > 1` 哨兵断言防单块空跑。它与 `check_no_loss` 是互补关系：后者只看整体拼接能否还原，属宏观等价；前者能定位到具体哪一对相邻块的重叠区没对齐。

第 2 项的落地形态是 `check_max_chunk(chunks, max_chunk_size)`：取所有块中最大的字符长度与上限比对，返回「是否通过 / 最长块字数 / 最长块文本」三元组，`__main__` 中以断言卡住，超限时报出实际字数与上限。

第 1、2 项同样做了反向验证：人为改坏某块的结尾 → 边界校验与重叠一致性同时报警；注入一个 347 字的超长块 → 分块长度校验报警，而边界校验放行（它判的是结尾字符是否合法，与长度无关，两项判定口径不同、各管一摊）。

第 3 项的落地形态是 `check_no_loss(chunks, original, overlap)`：把每块的前缀重叠切掉后拼接还原全文，与原文逐字比对，返回「是否一致 / 还原长度 / 原文长度 / 首个差异说明」四元组；同样配了哨兵断言（`len(chunks) > 1`，防单块空跑）与一致性断言。第 4 个返回值是后补的，起因是一个盲区：最初只回两个长度，遇到「长度相同、内容被改」的情况会报出两个一模一样的数字（还原后长度 230 / 原文长度 230），断言确实拦下了，但报错信息里看不出问题在哪；现在会给出首个差异字符的下标及前后各 8 字的对照。

**已修（2026-10-09）：`overlap=0` 场景已覆盖。** 原写法 `prev[-overlap:]` 在 `overlap=0` 时等于 `prev[0:]` → 取到整个前一块（**切片静默返回全部、不报错**），每块重复上一块全文，实测**还原 263 / 原文 230**；`check_no_loss` 的 `chunk[overlap:]` 同步失效。改法：拼前缀前先判 `overlap > 0`，否则用空串（**拼接依据就是 `overlap`，0 就没有前缀**），并让 `actual_overlap` 按**实际拼上的长度**记录。

**实测（全语料 50 篇）**：`overlap=0` → **50 通过 / 0 失败 · 2028 块 · 还原逐字一致**；`overlap=30` → 50 通过 · 2567 块 · 校验① 真正比较 **2517 对**。

**残留（如实记录）**：`overlap=0` 下「重叠一致性校验」**真正比较 0 对** —— 它必然绿、却什么也没验；而 `assert len(chunks) > 1` 哨兵抓不到它（块数确实 > 1）。即 `overlap=0` 是**合法但无意义**的配置：能跑通，不能指望它验证「重叠」。参数校验覆盖 `max_chunk_size<=0` / `overlap<0` / `overlap>=max_chunk_size`，**`overlap==0` 现已覆盖**。

4. **迭代优化思路**
第 1、2、3、4、5 项验收指标已全部落地（第 1、2、5 项含反向验证）。后续将递归切分改为迭代栈实现，解决超长文本递归深度溢出风险；补齐文档注释，固化测试用例。

### 项目三：`tool_agent_langgraph.py` | LangGraph 版 ReAct Agent
1. **实现内容**
在「项目一」手写 ReAct 的基础上，用 LangGraph `StateGraph` 重构调度循环：五个节点（`agent_node` 推理、`tool_node` 执行工具、`finish_done` 正常结束、`finish_over_limit` 步数超限结束、`finish_repeat_limit` 重复调用熔断结束）+ 两条条件边（`route_agent` 决定继续调工具 / 终止，`route_after_tools` 决定回推理 / 熔断收尾），复用 `tool_agent.py` 中全部工具定义、工具映射、重试装饰器与最大步数配置，工具层零改动。另挂 `SqliteSaver` checkpointer 把状态落盘到脚本同目录的 `checkpoints.sqlite`，支持跨轮对话记忆。

2. **核心问题与解决思路**
   - **问题1：消息历史手动拼容易出错**
     项目一里每轮手动 `messages.append(...)` 维护完整历史；LangGraph 版声明 `Annotated[list, add_messages]`，节点只返回本轮增量消息，框架自动追加进历史，不用再手动拼列表。
   - **问题2：循环终止条件要显式落地成边**
     手写版靠 `while...else` 区分「模型主动结束 / 步数超限」；LangGraph 版把这两个终止条件收进 `route_agent` 条件边——无工具调用返回 `"done"`、达到 `DEFAULT_MAX_STEPS` 返回 `"over_limit"`、否则返回 `"tools"` 进入工具节点再回到推理节点，形成「推理-行动-观察」闭环。为让结束原因可追溯，两条终止路径分别接到专用结束节点 `finish_done` / `finish_over_limit`，各自写入 `finish_reason` 字段并在运行末尾打印，正常完成与超限结束一目了然。
   - **问题3：初始状态缺字段会抛 KeyError**
     `agent_node` 会读 `state["step"]`，运行末尾也会读 `state["finish_reason"]`，所以 `__main__` 里初始状态必须显式给 `step=0` 和 `finish_reason=""`，否则取值时报 KeyError。
   - **问题4：跨轮对话记忆需要持久化状态**
     没有 checkpointer 时，每次 `invoke` 都是独立会话，第二次调用不知道上一轮说过什么。挂上 checkpointer 后，用同一个 `thread_id` 即可让多次 `invoke` 共享状态，`messages` 经 `add_messages` 自动续上历史。`__main__` 里用第二次 invoke 问「我上一条问了你什么」，再断言 `len(state2["messages"]) > len(final_state["messages"])` 验证记忆确实生效（消息数增长，否则说明 checkpointer 没起效）。最初挂的是 `InMemorySaver`，但它的存档只活在进程内存里、脚本一结束记忆就没了，只适合调试；现改为 `SqliteSaver`，状态写进 SQLite 的 `checkpoints` / `writes` 两张表，同一个 `thread_id` 换个进程也能续上。
   - **问题5：存档路径用相对路径会「记忆凭空消失」**
     `sqlite3.connect("checkpoints.sqlite")` 是相对路径，而相对路径的基准是**运行时的工作目录（CWD）**、不是脚本所在目录：从 PyCharm 里运行、在终端 `cd` 到别处运行，会分别解析成不同的文件（`sqlite3.connect` 还会顺手新建一个空库），表现为「换了个地方启动，记忆就没了」。解决：`DB_PATH = os.path.join(os.path.dirname(os.path.abspath(__file__)), "checkpoints.sqlite")`，用脚本自身位置锚定，从任何目录启动都读写同一份存档；会话标识也从硬编码提为顶部常量 `THREAD_ID`，为上服务时「从认证态派生」留出改造点。
   - **问题6：模型可能在同一工具上死磕 → 加第二道闸门（重复调用熔断）**
     只有 `DEFAULT_MAX_STEPS` 一道闸门时，模型换着工具调一样能烧完额度；于是针对「连续同一个调用」再加一道：`state` 增 `last_tool` / `repeat_count` / `repeat_breach` 三个**覆盖型**字段（语义是「当前」连续到第几次、不是历史累计，所以不能用 reducer），`tool_node` 里按「工具名 + 参数」签名逐个推计数、**执行前**判限，超过 `MAX_REPEAT`（默认 3）的第 4 次请求不执行，并把本轮剩余调用各补一条「未执行」的 tool 消息 —— 否则 `assistant.tool_calls` 与 tool 回复数量不匹配，下次调模型会直接 400。熔断后由 `route_after_tools` 条件边导向 `finish_repeat_limit` 收尾（而不是抛异常中断：抛异常会让图停在中间、`finish_reason` 写不进、存档留半截状态）。重置四时机：换工具、本轮推理结束（收尾节点归零）、新一次 `invoke`（入参归零）、参数不同即算新调用。验证方式是 6 个边界用例（同工具×4 / 换工具 / 不同参数 / 同参数×4 / 路由函数 / 带脏计数进入），不依赖真机调模型。

3. **项目总结**
工具层零改动，只替换「调度循环」这一层：手写 `while` 循环 → 框架状态图；跨轮记忆交给框架自带的 checkpointer 白拿，而「重复调用熔断」这类护栏（guardrail）要自己在状态里建模、再落到条件边上。两者对照能讲清 ReAct 的核心是「推理-行动-观察」闭环，具体用循环还是状态图实现是次要的。

### 变更卡 03 · `ChunkPosition`（裸字符串 → 带位置的对象）
- **改了什么**：分块返回值从 `list[str]` 升级为 `list[ChunkPosition]`（`text` + 7 个元数据字段），并在循环里用 `cursor` 游标顺推位置；`@dataclass(frozen=True)` **硬冻结**。
- **为什么**：RAG 需要的每一种「关于内容的信息」（从哪来、在哪、属于哪节、有没有被截断）**只在分块那一刻产生，之后再也算不回来** —— 载体必须换成「内容 + 坐标 + 出身」的对象。硬冻结保护的是**坐标这一事实**（三条不变量）不被事后偷改；要改字段只能走 `dataclasses.replace()` 派生新对象。
- **怎么验证**：三不变量可自证（`原文[start:end] == text` / 末块贴尾 / 首块贴零，代码里就是那两条 `assert`）；坏块 39 → `原文[3698,3822)` → **第 146–148 行 ·《八、📌 债清单》**。

### 变更卡 04 · frontmatter 清理（空格占位，不删字）
- **改了什么**：`build_corpus()` 每篇分块前，若 `text.startswith("---")` 且能找到闭合 `\n---`，把 frontmatter 整段替换为**等长空格**；找不到闭合则原样处理（不报错，也不静默吞掉整篇）。
- **为什么**：frontmatter 的 `tags / 类型 / 来源 / 关联` 主题词密度极高，向量化后会占住 top-1~3 的高分位。10-18 实测：问「什么是RAG？」，返回的 top-3 全是 frontmatter 残片与 markdown 表格分隔线，模型只能诚实拒答。
- **为什么用空格占位而不是删掉**：删掉会让本文件之后所有 `start / end / 行号` 整体前移 ⇒ 出处全错，而且**完全不报错**（静默错）；`ChunkPosition` 的三条不变量（`原文[start:end]==text` / 末块贴尾 / 首块贴零）会当场失效。空格占位**长度不变** ⇒ 位置不失真，同时 frontmatter 不再参与语义打分。
- **怎么验证**：全库块数 **2888 → 2878**（frontmatter 变成连续空格，段内分隔符消失，切分点少 10 处）；块坐标仍可对回原文。

### 变更卡 05 · Eval 基线（10 题 · Recall@3）
- **改了什么**：新增 `eval_rag.py` —— 固定 10 题 + 每题 gold 文件列表，`top_k=3`，按「命中文件名 ∈ gold」统计 Recall@3。
- **为什么**：四道校验只回答「管道通不通」，不回答「检索对不对」；没有指标时，任何一次改动都无法验收（10-14 之后一周的改动全部说不清是变好还是变坏）。
- **怎么验证**：本机实测 `Recall@3 = 8/10 = 80%`；其中 Q8（删掉 Observation 后为何第一反应是 API 报错）、Q9（`done` 字段为何用 `not`）判 FAIL，实得文件与 gold 无关。
- ⏱ **口径变更说明**：本卡数字是 `K=3` 时的历史值。2026-10-24 起脚本改为 `K=5`，同一套题得 `Recall@5 = 9/10 = 90%`。**@3 与 @5 不可直接比较**（K 越大越容易命中），对照请用同一 K。详见「变更卡 07」。
- **⚠️ 已知局限**：判定是**文件级** —— top-3 只要有一块来自 gold 文件就算命中，**看不见「块内容是垃圾」**。frontmatter 清理前后 Recall@3 都是 80%，正是这个盲区的直接证据。块级判定（正文是否真能回答 / 是否被污染）为下一步。

### 变更卡 06 · RAG 服务化（`FAST_API.py` · `POST /ask`）
- **改了什么**：新增 `FAST_API.py`，把六环包成 HTTP 接口。**装载区**（语料加载 / 分块 / 批量 `encode`）只在启动时跑一次；**请求区**（检索 / 裁剪 / 组装 / 生成）每次请求跑一次。`sources` 采集刻意放在**裁剪上下文之前** —— `clip_context_by_max_token` 会把块收成 `str` 返回，之后 `pos`（里面的 `source` / `start` / `header`）就再也取不回来了。
- **为什么**：前三个产出都是「能跑但点不开」，对方无法验证，等于不存在。服务化是「能点开」这一条的唯一解法，也是脚本与工程的分界线。
- **怎么验证**：三道判据全过 —— ① `Uvicorn running on http://127.0.0.1:8000` 且进程不退 ② `/docs` 返回 `200` ③ `POST /ask?q=什么是RAG？` 返回 `answer` + **5 条** `sources`（文件名 + 行号 + 标题），实测 **1.3 秒**。
- **⚠️ 过程中踩到的四个坑（记下来，因为定位过程比功能本身更能说明工程能力）**：
  1. **退出码 `0` ≠ 服务已启动**：缺 `if __name__ == "__main__": uvicorn.run(...)`，脚本执行完装载区就自然结束，`/ask` 一次都没被调用过。**满屏日志 + 退出码 0，比完全不跑更能骗人。**
  2. **`pip install fastapi` 不带 `uvicorn`**：FastAPI 只负责路由、参数校验、序列化；监听端口的是独立安装的 ASGI 服务器。
  3. **`list[dict]` 冒充 `list[ChunkItem]`**：`retrieve()` 读的是 `item.vector`（点号），dict 只能 `item["vector"]`（方括号）。类型不对**不在启动时炸，只在第一次请求时炸** —— 而它被坑 1（服务根本没起）完美掩盖了。
  4. **`HF_ENDPOINT` 镜像响应慢导致启动静默挂死**：`sentence-transformers` 启动时会向 HuggingFace 询问模型是否有新版本，网络卡住时表现为「不报错、不退、CPU 0%」。定位靠三步：**① CPU 累计值 4 秒增量是否为 0**（0 = 在等，不是慢）**② 进程有无 `Established` 外网连接**（有 = 卡在网络）**③ 端口有无 Listen**（有 = 其实早已启动成功，`uvicorn` 接管主线程后本来就不再输出）。修法：模型已本地缓存时设 `HF_HUB_OFFLINE=1`，让启动不依赖网络。

### 变更卡 07 · 评测口径 `K=3 → 5`（Recall@K 可调）
- **改了什么**：`eval_rag.py` 把检索条数抽成常量 `K = 5`（原来两处写死 `top_k=3`），输出从 `Recall@3` 改为 `Recall@{K}`；`basic_rag_pipeline.retrieve()` 的默认 `top_k` 由 `2` 改为 `5`，`__main__` 里演示查询同步 `top_k=5`。
- **为什么**：评测集（10 题）和 K 必须解耦。原来 3 写在两个地方，改一处忘一处会得到两套口径；抽成常量后「改 K」只动一行，且输出标题自动跟着变，不会出现「标题写 @3、实际按 @5 算」这种静默错。
- **怎么验证**：本机实跑 `python eval_rag.py`
  - 语料：`扫描 90 篇 → 入选 59 / 排除 31`；`docs=57 errors=2`（2 篇不是合法 UTF-8，已跳过并报告，不静默丢）
  - `Recall@5 = 9/10 = 90%`：Q1–Q7 PASS、Q10 PASS；Q8（删 Observation 后为何 API 报错）FAIL；**Q9（`done` 字段为何用 `not`）由 @3 的 FAIL 转 PASS**
  - 旧口径对照：`Recall@3 = 8/10 = 80%`
- **⚠️ 结论必须看清这一条**：`80% → 90%` **不是检索变好了**，是**尺子变松了** —— K 从 3 提到 5，多给两个位置，命中概率自然上升。两个数字**不可直接比较**，也不能拿去证明 frontmatter 清理有效（那次是 80%→80%，本来就没动）。
- **下一步**：真正能反映改善的是**块级判定**（该块正文里有没有答案 / 是不是 frontmatter 污染），不是把 K 调大。

### 变更卡 08 · 评测线重构（四层结构 + 块级判定 + 存档对比）
- **改了什么**：`eval_rag.py` 拆成四层 —— 数据层 `EVAL_SET` / 检索层 `make_searcher()` / 指标层 `_match_chunk`·`compute_metrics` / 报告层 `print_table`·`save_run`·`compare_last_run`。判定从「只看文件名」升级为「文件名 + 正文含逐字关键词」；新增 `MRR`、`avg_rank_hit`；每次运行存档并与上次对比给结论。修掉一处循环嵌套 bug（内层 `for ... in EVAL_SET` 覆盖了 `q`/`gold`，导致每题打印 10 行、题目永远是最后一道）。
- **为什么**：原版只能证明「召回了对的文件」，证明不了「召回的那块能答」；也没有存档，改完只能跟记忆比。做过一版「文件级全绿」而检索实际是垃圾——这正是需要用块级指标拦住的假绿。
- **怎么验证**：语料 69 篇 / 库 3918 条。块级判定上线后 `doc_recall@5 = 1.0`、`chunk_hit@5 = 1.0`、`MRR = 0.583`、`avg_rank_hit = 2.1`，单次运行 **1.1 秒**（重构前几十秒：原来每题把全库相似度算了两遍）。
- **踩坑记录（可作面试素材）**：关键词最初凭记忆写成概念名（`负零索引等价`、`终止条件取反`、`静默退化`…），**30 个里 30 个在语料中不存在**，`chunk_hit` 一度归零；当时 `doc_recall` 仍为 0.9 —— **两个指标分开看，才定位到是考卷错而不是检索坏**。此后定死规则：关键词只能从原文复制。
- ⚠️ **已知局限**：现 10 题为宽版 gold（参考检索结果标注，存在测试泄漏），只作回归集；衡量进步需闭卷难例题。详见 [评测线-设计与踩坑.md](评测线-设计与踩坑.md)。

### 变更卡 09 · 运维三件套（`/health` + 接口清单 + 请求分段计时）

- **为什么**：改动前服务答错了，只能去翻启动时那一屏日志，翻不到就只剩「感觉不对」；改动后任何人在任何机器上 `curl /health` 就能看见库对不对得上。这是「工程级」与「能跑」的分水岭 —— 接手的人不用读代码就知道服务健不健康。
- **关键设计**：`/health` 不只返 200，还把 `corpus.chunks`（当前语料分块数）与 `index.chunks`（库内条数）并排吐出；不一致时 `status=degraded`，`hint` 里直接写修法。**「200 不等于健康」** —— 库过期时服务照样 200、照样答，只是答的是旧数据。
- **怎么验证**：本机 `/health` 返回 `corpus.chunks = 3918`、`index.chunks = 3918`、`status = ok`、`chunk_failures = 0`。

- **改了什么**：`notes_loader.EXCLUDE_DIRS` 更新为新目录名（`复习材料` / `04-变更卡` / `03-变更卡`）；哨兵① 从「只看第一层 `root.iterdir()`」改成「用 `root.rglob('*')` 查整棵目录树」；提示文案同步为「在整棵目录树里都找不到」。
- **为什么**：2026-10-26 笔记库做了三章重构，`07-求职复习` → `91-求职与面试/复习材料`、`98-代码变更卡` → `02-RAG项目/04-变更卡`。**目录被挪到了第二层**，而旧哨兵只查第一层 ⇒ 会当场误报「名字写错了」。**假红也是 bug** —— 一条误报会让后续所有报警都失去信任。

### 变更卡 11 · 一条命令入口 `RAG_main.py`（自带冷启动建库）
- **改了什么**：新增 `RAG_main.py`，`python RAG_main.py "问题"` 一条命令完成「检索 → 裁剪 → 生成 → 出处」。拆四个函数：`ensure_index`（冷启动）/ `retrieve_context`（检索 + token 预算裁剪）/ `ask_llm`（拼 prompt + 调模型）/ `print_sources`（出处人类可读）。库不存在时自动 `load_docs → build_corpus → encode → build_index`，建完对账（块数 == 库内条数）再继续。
- **为什么**：之前要三步（先 `chroma_build.py` 建库、再起服务、再 curl）。现在一条命令，且别人 clone 下来不用先建库 —— 这是「能跑」和「能交付」的分界。
- **怎么验证**：① 无参数 → 打印用法、退出 0；② 正常路径 → 答案 + 5 条出处（文件名 + 字符区间 + 小节）；③ 冷启动（用临时 `CHROMA_DB_PATH` 隔离测试，未动真实库）→ 打印「正在建库」→ 建库完成 2713 块 = 库内 2713 条 → 继续检索回答；④ `py_compile` 通过。
- **已知不足（待修）**：① 冷启动时 `build_corpus` 的调试 print 未静音（可从 `FAST_API.py` 的 `redirect_stdout` 处理照抄）；② `ensure_index` 里 `except Exception` 过宽，会吞掉「库被占用」这类可诊断错误。
- 💡 **顺带发现（写进踩坑）**：测「为什么 overlap 不能设得很大」时模型答「知识库中没有相关内容」，查明是分块把问答拆成两块——引子块含「**答**：三个代价。」但正文表格在下一块且未被召回。**拒答是正确行为**；但它暴露出评测线的盲区：`chunk_hit` 的关键词若落在「引子块」，测的是「引子被召回」而不是「答案完整」。修法：gold 关键词改取答案正文里的词（如 `检索重复`）。

### 变更卡 12 · 语料白名单（黑名单之外，再上一道正向约束）
- **改了什么**：`notes_loader` 新增 `INCLUDE_TOPS = {"01-初始知识点", "02-RAG项目", "03-Agent项目"}` 白名单，与原有 `EXCLUDE_DIRS` 黑名单**叠加**（先过白名单定范围，再过黑名单剔细节）；哨兵从两条扩到三条，新增「白名单**外面**还有哪些顶层目录」。
- **为什么**：黑名单只能挡住**已知的**不要的东西，挡不住**以后新建的**未知目录 —— 哪天多一个 `04-xxx`，它的笔记就静默进了语料，把检索污染成来源不明的杂讯。两道闸门的失效方向相反：**黑名单失效 = 静默变多**（脏数据进来，检索变差但能看出来），**白名单失效 = 静默变少**（整章内容消失，而篇数只是"看起来正常变少"，最难发现）⇒ 所以针对白名单必须专门加哨兵③，把"外面还有哪些目录"每次都摆在屏幕上。
- **怎么验证**：`python notes_loader.py` → `扫描 111 篇 → 入选 50 篇｜排除 61 篇`，三条哨兵均不响（空差集本身就是一次验证）；同时打印 `ℹ️ 白名单外·整目录不入语料：.workbuddy, 00-总览, 90-计划与复盘, 91-求职与面试, 99-原始存档` —— 被挡在门外的目录一眼可见，不需要去读代码。

### 变更卡 13 · 评测结论判定改为以 MRR 为主
- **改了什么**：`eval_rag.py` 的 `compare_last_run()` 判定依据从「`chunk_hit` 升没升」改成「`MRR` 相对变化率 + 平均位次」，阈值 ±1%；命中率不再作主判据，只作退化拦截（`curr_hit < prev_hit` 依然直接判负向）。
- **为什么**：命中率**已经封顶在 1.0，再好也涨不动**。拿一个已经到顶的指标当主判据，等于宣布"以后所有改动都是无影响"—— 判据本身失去了分辨率。而 MRR 与 `avg_rank_hit` 还有空间：同样 5 条里都有正确答案，**排第 1 和排第 4 是用户体验的天壤之别**。
- **怎么验证（做了一次可复现的反向实验）**：把检索结果的前 5 条倒序 ——
  | 指标 | 原始 | 前 5 倒序 | 反应 |
  |---|---|---|---|
  | `doc_recall@5` | 1.0 | 1.0 | **看不见** |
  | `chunk_hit@5` | 1.0 | 1.0 | **看不见** |
  | `MRR` | 0.633 | 0.28 | −55.8% |
  | `avg_rank_hit` | 2.0 | 3.9 | 后移 1.9 位 |

  改回原顺序 → `MRR` **+126.1%**、命中率不变。**正负两个方向都亲眼见过，判据才算可信**（只见过一次变化方向，分不清是信号还是噪声）。
- ⚠️ **报变化率时必须带上绝对值**：同一次位移从 0.28 涨到 0.633 是 +126.1%，反过来从 0.633 跌到 0.28 是 −55.8% —— 百分比的分母不同，同一个事实能说出两个吓人的数。只报百分比不报绝对值的，是外行。

### 变更卡 14 · 纯空白块过滤（校验口径 ≠ 入库口径）
- **改了什么**：`build_corpus()` 把两个口径拆开 —— **校验用全量块**（含纯空白块），**入库前**才 `ps = [p for p in ps if p.text.strip()]` 滤掉，并按过滤后的顺序重排 `index`；分块算法本身一行没动。
- **为什么**：变更卡 04 用**等长空格**占位 frontmatter（为了不挪位置），而那串空格会被 `SEPARATORS` 里的 `" "` 切成独立的块 ⇒ **块 0 常常是 120 个纯空格**（`raw_chunk_max = 150 - 30`）。它对两件事的价值完全相反：
  - 对 `check_no_loss` 是**必需的** —— `restored_parts` 少了它，还原长度当场短一截，校验会误报"文本丢失"
  - 对检索是**纯垃圾** —— 向量近乎噪声，白占 `top_k` 名额，而且每个命中它的查询都会把出处打印刷成一大片空白
- **⚠️ 关键点：不能图省事在 `ps = [replace(...)]` 之后直接过滤** —— 那样 `check_no_loss` 会立刻误报。必须承认"校验的对象是分块算法，入的是检索单元"，两者边界本来就不同。
- **怎么验证（两种独立方法，结果一致才敢发布）**：
  - **白盒**（看 `build_corpus` 返回的内存对象）：入库 **2818** 块、纯空白 **0**、校验 **50 篇全通过 / 0 失败**；对账 `2818 + 62 = 2880` = 过滤前的全库块数 ✅
  - **黑盒**（绕过项目代码，直接 `col.get()` 读 Chroma 磁盘数据）：**2818** 条、纯空白 **0**、涉及 50 篇；最短 5 条仍有 35–45 字实质内容 ⇒ 没有误伤有内容的块 ✅
  - **回归**（重建库后跑评测）：`doc_recall@5 1.0→1.0`、`chunk_hit@5 1.0→1.0`、`MRR 0.633→0.633`、`avg_rank_hit 2.0→2.0` —— **四项全等**。这不是"白改了"，恰恰是"这 62 块本来就是零价值的垃圾"最硬的证据：删掉它们，gold 集的排名一位都没动。
