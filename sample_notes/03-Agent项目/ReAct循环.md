# ReAct 循环

ReAct = Reason（推理）+ Act（行动）。它让模型不是一次性把答案说完，而是**想一步、做一步、看结果、再想**。

## 一、为什么要循环

模型自己不知道今天的天气，也不知道数据库里有什么。它只能"说"。

ReAct 给的机制是：允许模型输出一个"我要调用某个工具"的请求，程序去执行，把结果再交回给模型，模型基于真实结果继续推理。

这样就把它从"凭记忆作答"变成"边查边答"。

## 二、一轮循环长什么样

一轮包含四步。

第一步，模型思考当前信息够不够。
第二步，不够就指定一个工具和参数，输出工具调用请求。
第三步，程序执行工具，拿到结果，以工具消息的形式回填给模型。
第四步，模型看到结果，判断是否已经能回答；不能就再来一轮。

终止条件通常有两个：模型不再请求工具（说明它准备好了），或者轮次达到上限（防止死循环烧钱）。

## 三、必须有的三道防线

**轮次上限**。没有上限，模型可能反复调同一个工具，费用和时间都失控。

**工具参数校验**。模型给的参数是它自己生成的，可能缺字段、类型不对、或者填了不存在的值。校验必须在执行工具之前做。

**异常隔离**。工具执行失败不能直接让整个循环崩掉，要把错误信息作为结果回填，让模型有机会换个做法。

## 四、最常见的坑

把工具调用的"请求"和"结果"在消息列表里的顺序搞反。

正确的顺序是：模型的工具调用消息在前，工具返回结果的消息在后。顺序反了，接口会直接报错，或者模型无法把结果和它的请求对应起来。

另一个坑是字段名。不同框架对工具调用字段的命名不一致，有的叫 tool_calls，有的把参数放在 function 里嵌套一层。照着旧教程写，经常在"点号后面接什么"这一步卡住。

## 五、用框架还是手写

手写一遍的价值在于：你会知道框架帮你做了什么。

LangGraph 版本和手写版本的核心循环是一样的，区别只是状态怎么流转、消息怎么归并、检查点存在哪里。先把无框架版本跑通，再换框架，才不会把"框架的便利"误当成"自己的能力"。
