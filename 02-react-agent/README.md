# 02 · 手写 ReAct Agent

**目标：不用框架，从零把 Agent 的循环写一遍；再用 LangGraph 重写，对照两种实现的取舍。**

---

## 一、为什么先手写，再用框架

| | 手写（`tool_agent.py`） | LangGraph（`tool_agent_langgraph.py`） |
|---|---|---|
| 循环 | `while` + 自己判断终止 | `StateGraph` 条件边 |
| 状态 | 局部变量，进程结束就没了 | `SqliteSaver` checkpointer，跨进程 |
| 改流程 | 改代码 | 加/删节点与边 |
| 适合 | 搞懂机制 | 生产 |

**先手写是为了在面试里能答「ReAct 到底是什么」——不是「我用了 LangChain」。**

---

## 二、手写版结构

```
用户问题
  ↓
LLM（带 tools 定义）
  ↓
有 tool_calls？ ── 没有 → 直接作答（出口 1：done）
  │ 有
  ↓
执行工具（4 类：时间 / 计算 / 文件 / 天气）
  ↓
结果以 role="tool" 回填 messages
  ↓
回到 LLM（循环）
  │
  └─ 达到最大步数 → 出口 2：over_limit
```

**关键设计：两个出口，而不是一个**

| 出口 | 含义 |
|---|---|
| `done` | 模型不再调工具 = 它认为信息够了 |
| `over_limit` | 步数耗尽 = 该停但没停，需要人看 |

⭐ 只有一个"最大步数"出口会掩盖问题：任务明明答完了，还是会报"超限"。
所以我加了一个实验：把 max_steps 调小，看能不能复现"任务已完成却被判超限"——能，于是改成双出口。

## 三、三个容易被追问的点

### 1. 同工具连续调用熔断

模型可能死磕一个工具（比如把参数改来改去反复调）。
规则：**同一工具连续 3 次 → 熔断，强制终止并给出原因。**

### 2. 异常分层重试

不是所有错误都该重试：

| 错误类型 | 处理 |
|---|---|
| 参数错误（缺字段 / 类型不对） | **永久性错误，不重试**，直接把错误回填给模型 |
| 网络抖动 / 超时 | 重试（有上限） |

⭐ 统一重试会把非幂等操作重复执行。

### 3. checkpointer 存的是什么

`tool_agent_langgraph.py` 用 `SqliteSaver`，按 `thread_id` 存快照。

- 存的是**每一步之后的快照，且历史全保留**（不是只留最新一张）
- 但它 **不是业务记忆**：它记的是图执行状态，不是"用户喜欢什么"
- 价值：杀进程重开能接着跑；不同 `thread_id` 的会话互不串

## 四、怎么跑

```bash
pip install -r ../01-rag-service/requirements.txt

# 手写版
python tool_agent.py "现在几点"
python tool_agent.py --max-steps 3 "帮我算一下 17 乘 23 再查现在几点"

# LangGraph 版
python tool_agent_langgraph.py "现在几点"
```

## 五、已知缺陷（如实写）

| 缺陷 | 说明 |
|---|---|
| 工具只有 4 个 | 没做大规模工具路由（工具多了怎么选、怎么控制权限，没做） |
| 没有成本预算 | 有 token 限制，但没有"这次任务花了多少钱"的统计 |
| 没有 trace | 只有打印日志，没落成结构化轨迹（这块在 `03-mini-pi` 里补上了） |

⭐ 面试被问到"你这块还缺什么"，答这三条比答"都做完了"可信。
